**Retrieval / Selection Method:**  
Retrieval is deterministic keyword-overlap matching implemented in `src/worker/knowledge/retrieve.ts`. The inquiry text and string values from `course_context` are concatenated, lowercased, normalized (punctuation removed except apostrophes and hyphens), and whitespace-collapsed. Each record keyword is matched with a word-boundary regular expression. Multi-word keywords receive weight 3; single-word keywords receive weight 1.5. Duplicate occurrences are capped at 2, and shorter overlapping keywords are removed. Scores are summed, records below `1.5` are discarded, results are sorted by descending score, and the top 3 records are selected. `formatKnowledgeContext()` projects each hit to `id`, `title`, `policy`, `default_route`, `human_review`, `review_note`, and `source`. The model receives these records in `state.retrieved_policies`. The fallback path uses the same retrieval; when no regex rule matches and the top score is at least 3, it uses the top record's category and default route.

## 4. One Controlled Improvement

**Selected Improvement:**  
More relevant grounding context. The improved request injects the top 3 retrieved policy records into Laya's `state.retrieved_policies`. The same retrieval is used by the fallback path: if no regex rule matches and the top score is at least 3, the fallback uses that record's category and default route. The Week 08 schemas, question instructions, and output validation were unchanged.

**Reason for Choosing It:**  
The baseline failed 9 of 10 cases. It had no authoritative policy context, so it frequently chose `context_needed`, missed required escalation, and routed schedule and access questions to the wrong owner. T08/F-02 had no regex match and defaulted to `other/escalate`, even though KB-INT-001 clearly covers academic dishonesty. Adding policy context directly targets the observed problem without changing the decision schema.

**Before Configuration:**  
Original Week 08 body in `scripts/evaluate-week08.mjs` (`buildBaselineBody`), corresponding to commit `c126430`:

```js
return {
  state: {
    inquiry_text: inquiryText,
    course_context: courseContext || {},
  },
  questions: {
    // category, route_to, confidence, escalate_to_human, rationale
  },
};
```

**After Configuration:**  
`buildImprovedBody` in `scripts/evaluate-week08.mjs`:

```js
const body = buildBaselineBody(inquiryText, courseContext);
const knowledgeHits = retrieveKnowledge(inquiryText, courseContext);
body.state.retrieved_policies = formatKnowledgeContext(knowledgeHits);
return { body, knowledgeHits };
```

Knowledge retrieval and projection are in `src/worker/knowledge/retrieve.ts`; records are in `src/worker/knowledge/course-policies.json`. The fallback switch is:

```js
const decision =
  version === "baseline"
    ? ruleBasedClassify(inquiryText)
    : ruleBasedClassify(inquiryText, knowledgeHits, true);
```

## 6. Before / After Comparison

| Metric | Before | After | Change |
|---|---:|---:|---:|
| Accuracy | 1/10 routing (10%); 1/10 strict (10%) | 5/10 routing (50%); 3/10 strict (30%) | +40 pp routing; +20 pp strict |
| p95 Latency | 7,875.97 ms | 14,887.86 ms | +7,011.89 ms (+89%) |
| Cost per Task | N/A | N/A | No metered cost; input tokens +135%; compute proxy roughly 2× |

**Cases That Improved:**  
- **T01 / N-01:** routing changed from `grading/instructor/no` to `grading/instructor/yes`. Context supplied KB-GRD-001, which explicitly requires human review. Strict still failed because confidence became `high` instead of `medium` and rationale remained `context_needed`.
- **T05 / E-02:** routing changed from `course_content/department_admin/no` to `course_content/student_support/yes`. KB-SUP-001 correctly moved access issues to Student Support. Strict still failed on confidence and rationale.
- **T06 / E-03:** became fully correct (`prerequisites/advising/medium/yes/policy_dependent/model`). KB-PRE-001 supplied the required advisor review and waiver rule.
- **T08 / F-02:** became fully correct. The knowledge-assisted fallback used KB-INT-001, which matched academic dishonesty/copied work and routed to the instructor with escalation.

**Cases That Became Worse:**  
- **T09 / D-01:** the clearest regression. Baseline at least had the correct `other` category; after grounding it became `course_content/student_support/medium/yes/policy_dependent`. Top-3 retrieval returned KB-SUP-001, KB-REG-001, and KB-CNT-001, and the model followed the support/content record instead of recognizing a mixed-topic case and escalating. It lost the only correct routing field (category) and became confidently misrouted to Student Support, even though escalation became `yes`.
- **T03 / N-03:** routing was already failing, but strict accuracy worsened because confidence dropped from the expected `high` to `medium`. The model still over-escalated a routine office-hours question.

**Trade-offs:**  
The change improves policy-dependent routing, but the gain is narrow. Excluding the two simulated fallback cases, model routing went from 0/8 to 3/8; one of the four new wins came from the KB-backed fallback. Strict accuracy is only 30% because confidence and rationale often remain wrong. The model still over-escalates clear cases (T02/N-02, T03/N-03), still misroutes vague or mixed cases (T04/E-01, T09/D-01), and cannot fix T10/D-02 because no strong record is retrieved for the implicit sequence question. Retrieval can also bias decisions: T09/D-01 got worse when multiple records were supplied. On the cost side, p95 latency roughly doubled and median latency went from 2,227 ms to 4,369 ms; input tokens rose 135%. There is no metered API cost because Laya is self-hosted, but the compute proxy is roughly 2×.

**Conclusion:**  
The improvement is worthwhile as a controlled step: routing accuracy rose from 10% to 50% and strict accuracy from 10% to 30%, with the largest gains on policy-dependent cases. It is not production-ready as-is. A 50% routing / 30% strict result and ~15 s p95 on CPU are too weak for real-time student triage, and the T09/D-01 regression shows that unfiltered top-3 retrieval can make mixed-topic decisions worse. I would keep the grounding-context direction, but fix escalation criteria, retrieval selection for mixed topics, and latency before shipping.

## 7. Engineering Reflection

**What I learned:**  
Grounding context is useful when the decision depends on an authoritative policy, especially for grade appeals, prerequisite waivers, and fallback cases with no regex match. It is not a substitute for decision reasoning: the model still over-escalates clear requests and still struggles with vague or multi-topic inquiries. Retrieval quality matters as much as retrieval existence; giving the model three plausible but conflicting records can push it toward the wrong single route. I also learned to separate routing accuracy from strict accuracy, because a decision can route correctly while confidence and rationale remain wrong.

**Why a few successful examples are insufficient:**  
The five A6 examples looked successful, but the controlled 10-case baseline passed only 1/10 on routing. Small examples did not expose over-escalation, missing fallback coverage, or the mixed-topic failure. A few examples also cannot show whether a change helps or hurts: T09/D-01 only became visible as a regression after running the same cases before and after. Repeated runs, pre-defined expected outputs, fallback cases, edge cases, p95 latency, and token usage are necessary to distinguish a real improvement from a lucky sample.

**What I would evaluate next:**  
Next I would test one change at a time: better decision instructions for escalation and mixed-topic handling, then top-1 or category-filtered retrieval to reduce T09/D-01 bias and prompt size. After that I would evaluate prompt compression, GPU/quantized inference for latency, confidence calibration on more cases, and a larger dataset with inter-rater agreement on expected labels. I would also test real traffic and monitor false auto-routes, because the cost of a wrong non-escalated route is higher than the cost of a conservative escalation.
