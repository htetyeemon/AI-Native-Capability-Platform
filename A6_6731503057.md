## 1. Problem and Capability

**Problem:**  
Students submit free-text questions about courses (e.g., prerequisites, scheduling, grading, login issues) to the course management platform. Currently, there is no automated way to classify these inquiries, so staff must manually read and forward each message to the correct department. This delays responses and creates unnecessary workload for support teams.

**Why AI?**  
The same intent can be expressed in many different ways (synonyms, typos, abbreviations, or mixed topics). Keyword and regex-based rules are brittle, require constant maintenance, and cannot handle ambiguity. An AI decision model can generalize across these variations and provide a confidence score along with a rationale, allowing for safe escalation to humans when uncertain.

**Input:**  
The API receives the inquiry text and optional course context. 

Example:
```json
{
  "inquiry_text": "I need to appeal my midterm grade, could you tell me the process?",
  "course_context": {
    "course_code": "CS201",
    "course_name": "Data Structures",
    "instructor": "Dr. Smith"
  }
}
```

**Expected Output:**  
A structured classification with the following fields:
- `category` (one of: registration, prerequisites, schedule, grading, course_content, instructor_contact, other)
- `route_to` (one of: registrar, department_admin, instructor, advising, student_support, escalate)
- `confidence` (one of: high, medium, low)
- `escalate_to_human` (yes/no)
- `rationale` (one of: clear_intent, mixed_topics, ambiguous, policy_dependent, context_needed)
- `source` (model or fallback_rules)

## 2. Decision Implementation

**Decision Configuration / Code:**  
The classification logic is implemented using Laya's Jev-compatible API (`POST /v1/systemone`). The schema is defined with `choice()` style criteria for each question. The full script is available at `scripts/classify-course-inquiries-laya.mjs`. The worker integration is implemented in `src/worker/index.ts`.

**Output Schema:**  
Each question uses typed `choice` with clearly defined criteria. All fields are required in the validated output. Allowed values are enforced both by the model schema and by application-level validation.

## 3. Platform Integration

**Architecture Diagram:**  


**Example API Request:**  
`POST /api/inquiries/classify` (Application Layer endpoint)

```json
{
  "inquiry_text": "I need to appeal my midterm grade, could you tell me the process?",
  "course_context": {
    "course_code": "CS201",
    "course_name": "Data Structures",
    "instructor": "Dr. Smith"
  }
}
```

**Example API Response (Happy Path):**

```json
{
  "status": "routed",
  "classification": {
    "category": "grading",
    "route_to": "instructor",
    "confidence": "medium",
    "escalate_to_human": "yes",
    "rationale": "context_needed",
    "source": "model"
  },
  "ticket": {
    "id": "T-9f3a82b1",
    "destination": "instructor",
    "escalated": true
  }
}
```

**Example API Response (Fallback):**

```json
{
  "status": "routed_with_fallback",
  "classification": {
    "category": "other",
    "route_to": "student_support",
    "confidence": "low",
    "escalate_to_human": "yes",
    "rationale": "policy_dependent",
    "source": "fallback_rules"
  },
  "ticket": {
    "id": "T-8c42ab76",
    "destination": "student_support",
    "escalated": true
  },
  "error": "fetch failed"
}
```

**Validation Rules:**

### Input Validation (Application Layer)
| Field | Rule | Error Response |
| :-- | :-- | :-- |
| `inquiry_text` | Required, string, trimmed, length between 10 and 2000 chars | `400 Bad Request` - "Inquiry text must be between 10 and 2000 characters" |
| `course_context` | Optional object. Only allow known keys. Values must be strings or null. | `400 Bad Request` - "Invalid course context" |
| Content-Type | Must be `application/json` | `415 Unsupported Media Type` |

### Output Validation (Application Layer)
| Field | Rule | Action if invalid |
| :-- | :-- | :-- |
| `answers` | Must exist and be object | Treat as model failure -> fallback |
| `category` | Must be in allowed set | Fallback |
| `route_to` | Must be in allowed set | Fallback |
| `confidence` | Must be `high`, `medium`, or `low` | If invalid -> normalize to `low` and escalate |
| `escalate_to_human` | Must be `yes`/`no` | If invalid -> force `yes` |
| `rationale` | Must be in allowed set | If invalid -> fallback |
| `answer_confidence` | Numeric 0-1 if present | If < 0.5 -> enforce escalation |

**Fallback Strategy:**  
If the model call fails (network error, timeout after 3s, HTTP >= 500, connection refused), JSON parse fails, or output validation fails, the system uses a deterministic rule-based classifier. The fallback applies keyword matching to route to appropriate teams (tuition/payments -> student_support, prerequisites -> advising, registration -> registrar, grades/appeals -> instructor, scheduling -> department_admin, login/portal issues -> student_support, instructor contact -> instructor). Unknown cases default to `route_to: escalate` with `escalate_to_human: yes`, `confidence: low`, and `source: fallback_rules`. The ticket is still created and logged; the user receives a confirmation rather than an error.

**Fallback Evidence:**  
Implemented in `src/worker/index.ts` via `ruleBasedClassify()`, `validateModelOutput()`, and try/catch with 3s timeout in the `/api/inquiries/classify` endpoint. When Laya is unavailable, the endpoint returns `status: "routed_with_fallback"` with fallback classification as shown above.

## 4. Engineering Reflection

**What worked:**  
Using Laya's Jev-compatible API made integration straightforward since the schema matched the example from class. The structured choice schema with >=3 options per question worked well, and all 5 test cases produced consistent, parseable outputs. Adding validation and fallback in the worker kept the system resilient.

**Unexpected behavior or mistakes:**  
Laya sometimes routes general tech issues (login/portal problems) to `instructor` instead of `student_support` depending on the phrasing. Also, when context was missing, the model often chose `rationale: context_needed` and set `escalate_to_human: yes` which is actually reasonable for safety. Initially, I tried using the `@typesafe-ai/sdk` but switched to direct HTTP calls to Laya since it was self-hostable and didn't require API credits.

**Production risks:**  
Running Laya locally means the service must be available 24/7 in production. Model latency, memory usage (checkpoints can be large), and lack of GPU on some hosts are concerns. Also, the confidence model is different from Jev's calibration - we need to validate thresholds on real traffic. Rate limiting, logging PII in `inquiry_text`, and prompt injection are other risks that need to be addressed.

**Next improvement:**  
Add request/response caching for common inquiries, implement proper audit logging to D1, add rate limiting, and fine-tune the fallback rules based on actual misclassifications. Also, consider using the Router with preloading in production and adding health checks for the Laya service with automatic fallback.
